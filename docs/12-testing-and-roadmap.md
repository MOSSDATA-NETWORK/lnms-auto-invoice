## 2. 计费引擎测试矩阵

每种计费规则至少覆盖正常、零值、空值、负值、边界和超大值。输入与期望结果使用十进制字符串或最小货币单位。

### 2.1 95 带宽

- `MAX` 分别命中入向和出向。
- `INBOUND`、`OUTBOUND` 忽略另一方向。
- `AGGREGATE` 使用聚合采样，验证结果不等于两个方向 95 相加。
- 95 为 0、缺失、超过端口速率和采样覆盖不足。
- bps 到 Mbps 转换及向上到 1、5、10 Mbps。
- 原始值刚好位于步长边界和仅高出最小精度。

### 2.2 保底、阶梯和封顶

- 实际用量低于、等于和高于保底。
- 基础费加超量、全量单价和最低计费数量。
- `GRADUATED` 与 `VOLUME` 在每个阶梯边界前、边界上和边界后。
- 最低消费、封顶、折扣、税和负调整组合。
- 封顶低于最低消费的无效配置。

### 2.3 账期与折算

- 28、29、30、31 天月份和闰年二月。
- 月中开通、月中停用、同日开通停用和跨时区边界。
- `[period_start, period_end)` 不重复计算结束时刻。
- 服务有效期完全早于或晚于账期时，`ACTUAL_DAYS`、`THIRTY_DAYS`、`NO_PRORATION` 和 `FULL_MONTH_IF_ACTIVE` 均计零。
- 账期跨两个价格版本时拆分明细，拆分合计与整段期望一致。

### 2.4 金额与税

- 0、2 和其他小数位币种。
- 行级税与账单级税的舍入差异。
- 含税价与未税价。
- 百分比折扣、固定调整和税基外调整。
- 大金额不溢出，Java 和 PostgreSQL 结果一致。

## 3. 领域与数据库测试

以下规则必须在真实 PostgreSQL 中验证：

- 同一计费项不能存在两个开放式 `CHARGE` 归属。
- 百分比分摊通过事务校验合计 100%。
- 同一正式编号和 `source_preview_id` 不能重复。
- 已发布价格、模板和审批版本不能修改内容。
- 已发布价格阶梯、模板资源和审批步骤不能增删改；非法负数价格、数量、阶梯和取整参数必须被数据库拒绝。
- 每一个租户内结构化外键都必须拒绝跨租户父子关系；原有 `ON DELETE CASCADE` 语义和任务引用的 `SET NULL` 行为必须保持。元数据测试必须逐一匹配原单列外键与 `(tenant_id, id)` 复合 companion 的子列、父列、动作、匹配模式和延迟属性，并拒绝重复映射；同时使用两租户真实 DML 验证跨租户引用返回 `23503`、级联删除不越租户且任务删除只清空 `job_id`。
- 正式账单冻结字段、明细、调整、文件关联和审计日志不能更新或删除。
- 直接 SQL 创建正式账单时，除 `FINALIZING`、`NOT_QUEUED`、`UNPAID`、`version = 0` 且生命周期时间全空外的任一初始状态都必须返回 SQLState `23514`；审批不是 `APPROVED`、审批指向其他预览、审批修订或审批前内容版本过期、预览未进入 `FINALIZING`、正式抬头或金额与预览不同也必须失败。失败插入不得留下正式账单，合法初始状态必须成功。
- 正式明细和调整必须拒绝空来源、跨预览来源、排除明细、非 `ACTIVE` 调整、重复来源和任一快照列篡改；确认时缺少或多出任一应入账来源必须失败。预览进入 `FINALIZING` 后，其明细、调整和排除项的 INSERT/UPDATE/DELETE 都必须被数据库拒绝。
- 正式账单确认必须拒绝缺失、空文件、错误 MIME、哈希或模板/渲染器信息不一致以及已软删除的 PDF；确认、首次发送、作废时间不得被清空或改写，发送成功不能停留在 `CONFIRMED`，没有等额有效付款分配时不得伪造 `PAID`。
- 发布与子表写入、正式化与审批动作、正式明细与证据关联的并发事务必须被父行锁串行化，冻结后写入必须失败。模板发布、用量快照转正式、正式明细引用、`invoice_files`、正式调整附件和付款附件都要用真实双连接测试验证文件元数据更新被正确等待并在冻结后拒绝。
- 用量证据链接在两个预览快照/文件之间反向并发移动时，必须按“全部快照 UUID -> 全部文件 UUID”的统一顺序完成，不能出现锁序死锁；测试应先用独立文件行锁把两个事务停在旧锁序的危险窗口，再释放并验证二者均提交。
- 正式审批动作、用量证据关联和底层文件元数据不能被篡改；付款、分配和退款历史不能物理删除或修改金额、归属等历史字段。直接 SQL 覆盖派生付款状态、插入初始 `REVERSED` 分配或提交空白冲销原因必须失败，合法分配、冲销和确认退款必须自动派生正确状态且每次只递增一次付款版本；退款状态未变化的 `UPDATE` 不得递增付款版本。
- 付款分配 INSERT 和 `ACTIVE -> REVERSED` 必须在同一事务内同步派生账单的 `UNPAID`、`PARTIALLY_PAID`、`PAID`、`OVERDUE`，正确设置或清空 `paid_at` 并只递增一次账单版本；应用服务不得再执行第二次手工状态更新。
- Flyway 空库测试必须核对所有应用/触发器函数均为 `SECURITY INVOKER`，且 `search_path` 按 `pg_catalog, public, pg_temp` 固定。付款余额回归必须在全新 JDBC 会话创建临时同名 `payments` 表，先复现未固定路径时的守恒绕过，再验证加固后返回 SQLState `23514` 且真实付款状态/版本不变。
- 同一付款的并发分配或退款必须先持有父付款 `KEY SHARE` 再由两个真实连接同时进入守恒触发器，验证父锁使用 `FOR NO KEY UPDATE` 串行化而不发生 SQLState `40P01`：总额未超限时两笔均提交并各递增一次版本，超限时只允许一笔提交，另一笔必须以守恒约束 SQLState `23514` 拒绝。
- 付款分配总额不能超过付款金额或账单未付金额。
- Worker 使用 `FOR UPDATE SKIP LOCKED` 时一条任务只能被一个 Worker 领取。
- 任务租约过期可被续领，原 Worker 迟到提交不能覆盖新租约结果。
- Outbox 与领域状态在同一事务提交。
- `docs/sql/001-initial-schema.sql` 必须能在空 PostgreSQL 16.9 上独立执行，并包含与最新 Flyway 相同的正式快照、更正关系和账单付款状态触发器。

每次数据库迁移都从空库执行，并从上一生产版本数据库升级执行。

## 4. LibreNMS 契约测试

仓库保存按版本分类的脱敏响应样本：

- Bill 列表和详情。
- 当前周期和上一周期。
- Bill History。
- 当前与历史图像。
- graphdata。
- 字段缺失、空历史、超时、限流和错误响应。

契约测试验证字段映射、单位、时区、History 选择和哈希稳定性。关键字段缺失必须失败，不能默认为零。

连接安全测试同时覆盖：空 `LIBRENMS_ALLOWED_ORIGINS` fail closed；协议、主机和非默认端口 exact match；默认端口与根路径规范化；
凭据、query、fragment 和非根路径拒绝；API 保存前校验；以及 Worker 对数据库旧值或配置漂移的请求时重验。预发布环境还要验证
Sync Worker 的出口网络策略不能访问云元数据、loopback 和未获准内网地址。

预发布环境对真实 LibreNMS 运行只读冒烟测试，不创建、修改或删除 Bill。

## 5. API 与幂等测试

- 所有命令型 POST 使用相同 `Idempotency-Key` 和相同请求时返回同一结果。
- 相同 Key 搭配不同请求体返回 `IDEMPOTENCY_KEY_REUSED`。
- `If-Match` 等影响命令语义的 Header 必须进入幂等指纹；相同 Key 搭配不同版本不得误回放。
- 异步命令完成后即使服务端资源版本已变化，相同原始请求和 Key 仍重放最初的 `202` 与任务 ID，不得把可变服务端状态混入请求指纹。
- 并发正式化只创建一张正式账单和一个编号。
- 过期 ETag 或版本号返回 `VERSION_CONFLICT`。
- RFC 9457 错误包含稳定 `code`、请求追踪 ID 和字段错误。
- UUID、金额字符串、日期和分页游标符合 API 约定。
- Webhook 重复投递使用事件 ID 去重，签名和时间窗口校验有效。
- OpenAPI 导出测试验证 `snake_case`、十进制字符串 Schema 和动态 JSON 对象；Orval 必须能从提交的静态契约重新生成且 TypeScript 构建通过。
- 前端 HTTP 测试验证生成路径只移除一次 `/api/v1`，不得向代理发送 `/api/v1/api/v1/...`。

## 6. 端到端关键路径

### 6.1 自动带宽账单

```text
创建客户和公司
  -> 创建业务、合同、95 计费项和价格版本
  -> 绑定 LibreNMS Bill
  -> 创建账单配置
  -> 同步完整 Bill History
  -> 生成预览
  -> 业务与财务审批
  -> 正式化并生成 PDF
  -> 发送通知
  -> 记录并分配付款
```

验收结果包括金额、用量快照、审批、PDF 哈希、发送记录和付款状态。

### 6.2 同一客户多账单

同一客户、公司和账期创建带宽、托管和 IP 三个配置。验证生成三张独立预览、三个正式编号、不同模板和币种，且没有计费项被隐式重复收费。

### 6.3 更正账单

作废有误正式账单，创建更正预览，重新审批并生成新正式账单。验证 PDF 确认前原账单保持 `VOIDED` 且没有 `REPLACES` 关系；PDF 成功持久化后，新账单 `CONFIRMED`、关系写入、原账单 `REPLACED`、预览 `FINALIZED` 和 `invoice.confirmed` Outbox 在同一事务提交。任一步失败时验证文件、关系、状态和 Outbox 全部回滚；已有付款仍会阻止未经处理的作废。

### 6.4 崩溃恢复

在正式编号分配后、PDF 上传前终止 Render Worker。租约到期后由其他 Worker 续领，验证继续使用原编号、只生成一个正式文件关联并最终进入 `CONFIRMED`。

## 8. 安全测试

- 租户 A 无法读取、修改、导出或通过错误消息推断租户 B 的对象。
- 每个角色验证允许和拒绝动作，前端隐藏不代替后端鉴权。
- 登录限速、会话撤销、TOTP、OIDC 回调和 CSRF。
- LibreNMS、SMTP、S3 和 Webhook 秘密不出现在 API、日志、审计差异或错误页面。
- LibreNMS 数据源不能越过 exact-origin allowlist；API 与 Worker allowlist 不一致时 Worker 必须拒绝连接，且不跟随跨目标重定向。
- 文件上传验证 MIME、扩展名、大小、哈希和恶意内容。
- 同租户用户 A 上传的文件不能被普通用户 B 绑定到导入任务或预览调整；`system.admin` 代绑定成功，文件不存在、已软删除和越权场景都统一返回 404。相同内容由不同用户上传时必须生成各自包含 `user_id` 的对象键和文件记录。
- CSV/XLSX 覆盖 ZIP bomb、解压总量/条目数、共享文本、稀疏超大行号、公式、超长表头和超长单元格。
- Render Worker 默认无网络，阻断 SSRF、DNS 重绑定、本地文件和元数据服务访问。
- Webhook 使用 HMAC、时间窗口、重放保护和密钥轮换。

高危安全场景失败时不能带病发布。

## 9. 性能目标与容量场景

首版容量基线：1 万有效业务、5 万月度账单明细。

建议验收目标：

| 场景 | 目标 |
|---|---|
| 常用后台查询 | P95 小于 500 ms，不含外部依赖 |
| 单账单纯计算 | P95 小于 2 s，100 条明细以内 |
| 1 万计费项批量计算 | 60 分钟内完成，可水平扩展 Worker |
| 普通 PDF 渲染 | P95 小于 15 s，失败可安全重试 |
| 同步任务领取 | 无重复处理，租约竞争下持续前进 |

性能测试必须使用接近真实的明细数量、JSONB 大小、索引和对象文件，不用空表结果代替。

## 10. 历史数据导入

首版支持 CSV/XLSX 主数据导入，顺序为：

```text
客户和公司
  -> 联系人
  -> 产品、业务和资源
  -> 合同
  -> 价格规则与合同计费项
  -> 账单配置与归属
  -> LibreNMS 映射
```

导入流程：

1. 上传文件并计算哈希。
2. 解析为暂存数据，不直接写正式表。
3. 校验必填、编号、外键、币种、日期、价格有效期和重复归属。
4. 生成错误报告和导入摘要。
5. 用户确认后在受控批次中写入。

确认阶段每行的正式表写入与暂存行 checkpoint 必须处于同一事务；失败行状态与错误详情同事务保存。最终统计从暂存行重新聚合，任务终态与 `import.completed` 审计同事务提交。故障注入测试必须覆盖 checkpoint 失败回滚、审计失败回滚以及重试后不重复资源、错误或审计。
6. 使用幂等键支持失败重跑，成功行不重复创建。

历史正式账单若需要导入，应单独设计只读归档流程，不能伪造本系统审批、计算或 PDF 证据。

## 11. 并行核对与上线

新旧流程至少并行两个完整账期：

1. 锁定客户、合同、价格和账单配置范围。
2. 新系统生成预览，但暂不自动发送。
3. 按计费项比较原始用量、计费用量、单价、税、调整和总额。
4. 差异大于一个最小货币单位时记录原因和处理人。
5. 连续两个账期达到验收标准后，分批开启正式化和发送。

上线批次优先选择规则简单、数据完整、客户数量少的业务。异常多或存在复杂手工处理的客户放在后续批次。

## 12. 发布质量门

进入生产前必须满足：

- 所有迁移可从空库和上一版本升级成功。
- 单元、集成、契约、端到端和安全必测集全部通过。
- 没有未解释的金额差异或高危安全问题。
- 正式化、Worker 崩溃恢复、幂等和租户隔离通过。
- 备份恢复演练通过，PDF 和证据文件可校验。
- 监控、告警、任务死信和运维手册可用。
- 自动生成和自动发送具有独立开关及紧急停用方式。
- API 与 Sync Worker 使用同一非空 LibreNMS origin allowlist，并以出口网络策略补强 DNS 重绑定防护。

本地 `mvn test`、TypeScript 构建、ESLint 和 Vitest 通过只代表快速质量门。没有 Docker/PostgreSQL、真实 LibreNMS 或浏览器端到端环境时，必须明确标记对应数据库迁移、Testcontainers、Compose、Playwright、性能和恢复验收为未执行，不能用 H2 或 Mock 结果替代。

前端快速质量门还包括固定 pnpm 版本重新生成 Orval 客户端、格式检查、依赖最短发布时间校验和受控安装脚本检查；不得为了让 CI 通过而关闭供应链策略。

## 13. 第一阶段实施顺序

1. 项目骨架、身份、租户、数据库迁移和审计。
2. 客户、公司、业务、合同、计费项和导入。
3. 版本化价格规则和纯计费引擎。
4. LibreNMS 适配器、映射和用量快照。
5. 账单配置、分摊和重复收费检测。
6. 预览、调整、异常和两级审批。
7. 正式化、编号、模板沙箱和 PDF Worker。
8. 邮件、付款、报表基础、监控和恢复演练。

每一步完成领域测试、API 测试、数据库约束和专题文档后再进入下一步。

## 14. 后续路线图

### 第二阶段

- 可视化模板编辑器、DOCX、多语言、多币种和汇率。
- 客户门户、在线确认、异议、完整付款和逾期提醒。
- 流量预警、SLA 自动赔偿、收入、应收和利润报表。

### 第三阶段

- CRM、工单、支付、ERP、电子发票和供应商账单。

- 多租户 SaaS、套餐、配额、租户管理员和租户品牌。

跨阶段功能必须通过新的威胁模型、数据模型和迁移评审，不能只在现有表中增加无约束 JSON 字段。

## 15. 完成定义

一个功能只有在以下条件都满足时才算完成：

- 领域规则和失败路径明确。
- API、数据库迁移和权限实现一致。
- 关键指标、日志和审计可观察。
- 自动化测试覆盖正常、边界、并发和租户隔离。
- 用户可见错误给出可操作信息。
- 对应 `docs/*.md`、OpenAPI 和测试矩阵已更新。
